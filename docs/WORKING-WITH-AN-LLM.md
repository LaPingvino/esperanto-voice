# Working with an LLM on a project like this

This project went from "no free Esperanto voice exists" to a released voice
that beats espeak-ng in one evening, mostly driven by a coding agent (an LLM
with shell access) and a human steering it. These are the lessons that made
the difference. They apply to most data and ML projects, not only speech.

## 1. Give it a workbench, not just a chat window

An LLM that can only answer questions makes you the copy-paste layer: you run
the code, paste the error, paste the fix back. Most of the time goes there.

An agent that can run commands, read the error and try again iterates in
seconds. In this project that covered a sandbox socket error, a broken ONNX
exporter, a missing compiled extension and an out-of-memory crash — each
diagnosed and fixed without a human touching the keyboard.

Give it a real (or sandboxed) environment, version control, and permission to
fail.

## 2. Set constraints and goals, not step-by-step instructions

What worked:

* "Prefer freely licensed over better quality."
* "Every iteration should take minutes, not hours."
* "The bar is: clearly better than espeak-ng."

Then let the agent find the path, and correct it when it drifts. Detailed
step lists turn the LLM into a slow typist; no goals at all lead to wandering.

## 3. Build the measurement before the thing

The first real artifact here was not a model but a test harness: synthesize
16 sentences, transcribe them with a speech recognizer, report an error rate
per sentence, `go test`-style. From then on every idea got a number within a
minute, and "it feels better" stopped being the only signal.

Ask for the evaluation first. It is cheap, and it changes everything after it.

## 4. Know who does what

| automate it | keep it human |
|---|---|
| Cutting recordings into sentences and matching transcripts (forced alignment) | Taste: does it sound natural? |
| Rejecting bad clips (recognizer confidence), listening only to borderline ones | Domain truth: how speakers actually talk, which sources to trust |
| Scoring every model version | Goals and trade-offs: free vs. better, fast vs. perfect |
| Reading licenses, model cards and issue threads, then summarizing | People: volunteers, collaborators, community |
| Choosing training data for coverage | Final listening and release decisions |
| Diagnosing and fixing tooling errors | Saying "stop, that's the wrong direction" |

A lot of manual labor in projects like this is automatable without anyone
realizing it. When something feels tedious, ask the LLM whether it can be
done automatically — often the answer is a fifty-line script.

## 5. Feed in domain knowledge at the right moment

Short human remarks saved hours here:

* "Real speakers glide j and ŭ like that too" — stopped a "fix" to something
  that wasn't broken.
* "That audio was generated by a non-commercially licensed model" — kept
  restricted data out of a free voice.
* "Focus on the course, the other project was just where I used voices before"
  — stopped scope drift.

The LLM knows a lot in general; you know your field and your situation.
Interrupt early and often.

## 6. Verify claims at the source

A website claimed a model was free for commercial use. The model card itself
said the opposite, and the maintainers confirmed it in their issue tracker.
Ask the LLM to check primary sources — model cards, license files, maintainer
statements — not summaries or marketing pages.

## 7. Make long jobs visible and resumable

Long-running jobs (alignment, training) should print progress you can read,
save results to disk as they go, and survive interruption. One run here sat
silent for 17 minutes because its progress bar didn't write to a log file;
after that, every job printed one line per step. A job you can't see is a job
you can't steer.

## 8. Cut corners deliberately

Separate fast experiments from the final polish. Here, the language-specific
part of the voice could be trained alone, several times faster, for all the
comparisons; the full, slow training runs once, on the winning recipe. Ask the
LLM where the time goes and what each shortcut costs — it can usually tell
you.
